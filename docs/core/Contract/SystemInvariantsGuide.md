# 系统级不变量整理与维护指南

本文定义系统级核心不变量的识别、分类、完整性检查和维护方法。具体不变量见 [系统级不变量规约](./SystemInvariants.md)，整体规约索引见 [行为规约](../Contract.md)。

本文中的分类、检查问题和维护步骤不直接构成系统行为约定。

## 1. 纳入边界

候选约束同时满足以下条件时，才纳入系统级核心不变量：

1. **持续成立**：约束在其适用期间的每个有效提交边界成立，而不只是描述一次操作的普通步骤；
2. **跨越边界**：约束涉及至少两个组件、两个状态所有者，或者跨组件消息、资源和生命周期阶段；
3. **影响全局正确性**：违反约束会破坏状态一致性、身份隔离、资源安全、协议完整性、确定裁决或流程终止；
4. **独立于实现机制**：约束不依赖线程、锁、通道、智能指针或运行时的具体选择；
5. **可判定**：能够指出适用范围、责任主体、必须保持的条件和违反后的处理。

以下内容原则上不纳入系统级不变量规约：

- 单个组件内部即可完整保证、且不影响跨组件契约的局部不变量；
- 具体数据结构、算法和运行时实现方式；
- 用例处理步骤的简单复述；
- 只影响展示文案或内部代码组织的约定；
- 尚未明确责任主体、适用边界或失败语义的设计意向。

一项局部约束如果是跨组件保证成立的必要前提，应在对应子文档中定义，并在系统级不变量规约中只保留跨组件结论。

## 2. 双轴检查模型

完整性检查使用两个相互独立的轴：

- **性质轴**回答“系统必须保持哪一类正确性”；
- **流程轴**回答“该类正确性必须在哪些端到端路径上成立”。

每个纳入范围的流程都必须检查全部性质；每条系统级不变量也必须映射到至少一个流程。

## 3. 性质轴

### 3.1 A1 权威与状态所有权

检查可变状态、外部能力和领域真值由谁唯一裁决：

- 每项状态由谁持有并提交转换；
- 哪个组件有权访问设备、存储或其他外部能力；
- 哪个组件可以触发不可逆副作用；
- 哪个对象是领域真值，哪些只是投影、缓存、快照或响应副本；
- 是否存在两个组件能够独立修改同一逻辑事实；
- 状态外准备与状态提交的责任是否分离清楚。

### 3.2 A2 状态合法性与守卫

检查跨组件状态组合及输入适用条件是否始终合法：

- 每个输入在哪些生命周期和组件状态下适用；
- 不适用输入应被拒绝、忽略还是视为致命错误；
- 多个组件状态是否可能形成互相矛盾的组合；
- 过渡状态是否具有明确含义和出口；
- 生命周期变化后，原业务状态是否仍然有效；
- 默认禁止的转换是否存在未经声明的旁路。

### 3.3 A3 身份、关联与作用域

检查每个异步输入只能作用于其原本关联的状态和资源：

- 标识由谁生成、在哪个范围内唯一以及何时可以复用；
- 请求、任务、输出、计时器、事件和资源使用什么标识关联；
- 会话级、任务级和资源级标识是否被混用；
- 迟到、重复或身份不匹配的输入如何识别和处理；
- 取消、更新和释放操作的作用域是否明确；
- 标识是否随所有需要关联的跨组件边界完整传递。

### 3.4 A4 原子性与提交一致性

检查对外可观察的成功边界是否与状态和资源的完整提交一致：

- 操作在哪个边界从准备转为已提交；
- 状态转换与资源取得或释放是否保持一致；
- 成功响应发出时，承诺的后置条件是否已经成立；
- 失败、拒绝、过滤或取消是否可能留下部分提交；
- 跨组件接受与本地状态提交之间是否存在不一致窗口；
- 是否可能发布部分构建对象或不完整领域事件。

### 3.5 A5 顺序、串行化与竞争裁决

检查竞争输入是否具有唯一且可实现的裁决规则：

- 哪个状态所有者负责串行裁决；
- 同一接收方和不同接收方分别保证什么顺序；
- 是否错误依赖发送时间、物理发生时间或业务时间；
- 完成、失败、超时、取消和关闭如何竞争；
- 首次决定是否会被重复或后续输入覆盖；
- 状态投影与可靠消息之间是否存在被错误依赖的观察顺序。

### 3.6 A6 资源生命周期与隔离

检查跨组件资源是否具有完整的创建、持有、转移、共享和释放路径：

- 资源由谁创建并在何时成为有效资源；
- 消息发送前后由谁持有释放责任；
- 借用是否越过同步边界或进入异步消息；
- 逻辑有效期与物理存活期是否被混淆；
- 失败、拒绝、过滤、过期和取消是否释放未提交资源及消息载荷；
- 已接受任务是否固定其执行资源；
- 资源替换、组件停止或模式切换是否错误地使其他合法持有者失效；
- 所有正常和异常终止路径是否有明确的资源处理结果。

### 3.7 A7 协议基数与交付语义

检查跨组件交互的次数约束和交付性质：

- 一个请求必须产生零次、一次还是多次响应；
- 一个被接受任务必须产生多少个终止输出；
- 哪些消息必须可靠交付，哪些值允许合并、替换或跳过；
- 重复请求应幂等确认、附着等待、拒绝还是视为错误；
- 消息重复、丢失或接收方关闭时采用什么处理；
- 是否可能对同一操作产生两个互相冲突的终止事实；
- 投影是否被错误用来代替响应、输出或关闭确认。

### 3.8 A8 不可变性、确定性与副作用边界

检查一次操作是否只受已声明输入影响，并且只产生已声明副作用：

- 跨组件发布的对象是否在发布后保持业务不可变；
- 执行是否读取未声明的共享状态或外部环境；
- 后续配置、Frame、模式或注册表变化是否影响已接受任务；
- 组件是否执行其边界外的设备、文件、数据库、GUI 或消息副作用；
- 缓存和派生产物是否跨任务泄漏；
- 同一组显式输入是否具有确定的解释和稳定的关联结果。

### 3.9 A9 进展、终止与故障边界

检查每个已开始流程是否具有可观察的正常终点或明确的异常终止出口：

- 接受后的操作由什么事实证明完成；
- 每个运行或过渡状态如何离开；
- 等待是否可能形成跨组件环或永久占用串行执行边界；
- 哪些步骤依赖协作终止，是否需要截止时间或最坏时间保证；
- 正常失败、业务拒绝、协作取消和致命错误是否明确区分；
- `panic` 是否被错误转换为业务结果或优雅终止；
- 组件关闭和资源释放满足什么条件后，生命周期才可终止。

## 5. 流程分解方法

每个流程按以下边界分解，不要求每个流程都存在全部边界：

1. **触发**：输入由谁产生，进入哪个接收边界；
2. **校验**：检查生命周期、状态、身份和业务守卫；
3. **准备**：取得临时资源并形成候选结果；
4. **接受**：接收方承担继续处理和最终终止的责任；
5. **提交**：状态与资源成为当前领域事实；
6. **完成**：通过响应、输出、事件或关闭确认形成可观察终点；
7. **异步后续**：完成边界后仍允许发生的消息和资源变化；
8. **失败与取消**：业务失败、过期输入、协作取消和致命错误的分支；
9. **释放**：每条终止路径上的资源与等待者处理。

如果同一流程存在多个提交或完成边界，必须分别命名，并说明其顺序和责任转移。

- **N6 无逐帧进展保证**：持续采集不承诺固定时间内必然产生新 Frame；Camera 停止的有界性由 F14 和 `SI-A9-10` 保证。

## 7. 本轮敲定结果

本轮矩阵没有空白单元格，也没有未决 `G` 项。原六项缺口按以下结论回写规约：

1. **G-01**：`ModeSessionId`、`inspection_id` 和 `frame_id` 在同一应用运行期间唯一且不得复用；标识空间耗尽或无法保证唯一时直接 `panic`；
2. **G-02**：可能阻塞的 Scheme Manager 操作在独立执行环境中完成，不设置截止时间；App Controller 等待期间可以处理 InspectionEvent 和维持 GUI 状态发布，但后续应用命令包括 Shutdown 必须排队，操作可以无限等待；
3. **G-03**：Camera 停止、Inspection Worker 关闭和 Actor 关闭分别使用应用级固定截止；对应截止先于确认被关机协调方处理时直接 `panic`；
4. **G-04**：进程内可靠消息每次成功发送恰好入队一次，不复制、不隐式重试；发送或接收基础设施失效直接 `panic`；
5. **G-05**：`Terminated` 不等待 GUI 本地不可变共享引用物理销毁；这些引用从 `ShuttingDown` 起失去业务逻辑有效性，不得触发业务操作；
6. **G-06**：保存成功保证同一运行环境中的原子替换和后续读取一致，不承诺掉电或操作系统崩溃后的持久性。

完成状态只表示当前文档和 v1 流程轴未发现未决缺口，不表示未来新增流程可以跳过重新检查。

## 9. 完整性判定

完成一轮梳理必须同时满足：

1. 流程轴列出的全部流程均已按流程分解方法检查；
2. 覆盖矩阵不存在空白单元格；
3. 每个 `N/A` 都有明确理由；
4. 每个 `G` 都已形成具体约定、进入明确讨论项，或通过范围调整排除；
5. 每条具体不变量至少覆盖一个流程，并能追溯到相关规约；
6. 同一领域事实不存在互相冲突的权威来源；
7. 每个接受边界都有对应完成、取消或异常终止路径；
8. 每项跨组件资源在所有终止路径上都有明确处理结果；
9. 每组竞争输入都有唯一裁决者和确定规则；
10. 局部不变量与系统级结论不存在冲突。

## 10. 维护步骤

新增或修改命令、申请、控制请求、任务、输出、事件、投影、跨组件资源、组件状态或生命周期阶段时：

1. 判断是否新增端到端流程；
2. 对受影响流程重新检查 A1 至 A9；
3. 更新覆盖矩阵及发现的缺口；
4. 新增、修改或删除具体系统级不变量；
5. 检查对应子文档中的局部不变量和完整性清单；
6. 确认 `Scope.md`、`Architecture.md` 与行为规约不存在冲突。
